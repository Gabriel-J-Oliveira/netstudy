ICMP + PING + TRACEROUTE · ÁREA 01

O que realmente descobrimos quando testamos a comunicação?

Ping não é apenas “ver se responde”

C:\> ping 192.168.50.30O QUE O COMPUTADOR ESTÁ FAZENDO?
ICMP é um protocolo usado junto ao IP para transportar mensagens de controle, erro e diagnóstico relacionadas à comunicação de rede.
OSI · CAMADA 3 — REDE

ICMP trabalha no contexto IP. O Echo estudado aqui não utiliza portas TCP ou UDP.

O comando Ping normalmente envia ICMP Echo Request ao destino e observa se recebe Echo Reply.

PC-AEcho Request →PC-B← Echo ReplyPC-A
PING TESTA UMA TROCA ICMP. ELE NÃO TESTA “TUDO”.

Request enviado · 0 msReply recebido · 23 msRTT · 23 ms

RTT, ou Round-Trip Time, é o tempo entre o envio da solicitação e o recebimento da resposta. Não é apenas o tempo de ida.

Agora sabemos que Ping é uma troca de mensagens. Vamos olhar as duas mensagens envolvidas.

ÁREA 02

Uma pergunta e uma resposta

ICMP ECHO REQUESTSource 192.168.10.20Destination 192.168.50.30

“Você consegue receber esta mensagem?”

ICMP ECHO REPLYSource 192.168.50.30Destination 192.168.10.20

“Recebi e estou respondendo.”

Request: A → R1 → R2 → R3 → B. O Reply retorna a A, mas em redes reais o caminho de volta não precisa ser idêntico ao caminho de ida.

Receber um Reply é evidência útil. Precisamos ser cuidadosos com o que concluímos.

Ping responde uma pergunta pequena, não todas as perguntas

Echo Reply evidencia que o Request chegou, o destino gerou uma resposta e ela retornou: havia conectividade IP suficiente para aquela troca ICMP naquele momento.

Podemos afirmar que o servidor está desligado?

Não. A mensagem ou resposta pode não ter sido entregue, filtrada ou perdida; roteamento ou disponibilidade também podem estar envolvidos.

TIMEOUT DIZ: “NÃO RECEBI A RESPOSTA ESPERADA.”
ELE NÃO DIZ AUTOMATICAMENTE: “O DESTINO ESTÁ DESLIGADO.”
✓ REPLY

Recebi resposta do destino.

⏱ TIMEOUT

Não recebi a resposta esperada no tempo.

⚠ UNREACHABLE

Recebi mensagem explícita de que algum ponto não conseguiu realizar uma entrega.

Reply from 192.168.10.1: Destination host unreachable.

Diferentemente do timeout, algum equipamento enviou uma mensagem ICMP explícita.

Ping funciona, aplicação não. Qual afirmação é mais segura?

AUSÊNCIA DE RESPOSTA NÃO É UMA CAUSA. É APENAS UMA EVIDÊNCIA.

Ping não mostra cada roteador. Para isso, precisamos compreender TTL.

ÁREA 04

Um pacote não pode circular para sempre

TTL é um campo do IPv4 que limita quantos saltos de roteamento um pacote pode atravessar.

Apesar do nome histórico “Time To Live”, no encaminhamento IPv4 moderno ele é reduzido a cada roteador.

A · TTL 3→ R1 · TTL 2→ R2 · TTL 1→ R3 · TTL 0 · descarta

Quando expira, o roteador normalmente pode enviar ICMP Time Exceeded à origem.

TTL LIMITA ATÉ ONDE O PACOTE PODE IR.

E se fizermos isso de propósito?

Traceroute envia sondas com TTL progressivamente maior: TTL 1 revela R1; TTL 2, R2; TTL 3, R3; TTL 4 alcança B.

TRACEROUTE NÃO PERGUNTA “QUEM ESTÁ NO CAMINHO?”.
ELE CONTROLA ATÉ ONDE CADA SONDA CONSEGUE IR.

Uma sonda sai com TTL 2. Onde expira?

C:\> tracert 192.168.50.30
  1    1 ms    1 ms    1 ms    192.168.10.1
  2    8 ms    7 ms    8 ms    10.0.0.2
  3   15 ms   14 ms   16 ms    10.0.1.2
  4   23 ms   22 ms   24 ms    192.168.50.30

Cada linha apresenta múltiplas sondas; são tempos de resposta, não “velocidade”. Diferentes implementações podem usar sondas diferentes; aqui usamos o comportamento conceitual e o tracert do Windows.

1 R1
2 *
3 R3
4 destino

O hop 2 não responder não prova que parou de encaminhar. R3 e o destino responderam.

1. Ping usa qual protocolo no cenário?

Por que Ping bem-sucedido não prova que uma aplicação funciona?

Ping testa uma troca ICMP. Echo Reply mostra que ela chegou e retornou; o serviço precisa ser testado separadamente.

Explique antes de revelar

Como Traceroute descobre os roteadores sem conhecer o caminho?

Envia sondas com TTL crescente. Ao chegar a zero, o roteador pode responder com ICMP Time Exceeded, revelando progressivamente os saltos.
